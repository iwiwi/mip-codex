# 停滞したPhase Iの乗数候補を元MPSで検査する

main PR74/FP337のniddaは有効整数主解を得るが、Phase I目的が約0.152で進まない枝で数値停止する。候補乗数のfloat box矛盾だけを試した旧案は改善なしだった。今回は診断flag時だけ数値停止の候補乗数とnode bounds/元行対応を保存し、Python Fractionの元MPSで厳密な矛盾を探索する。候補を証明と混同しない。mainの停止/枝刈りを変えず、offlineで有効証明が得られた場合だけRustへの統合を検討する。

列/行スケールがある場合は乗数の単位を別途戻す必要がある。まずscaled counts=0のniddaに限定してデータの対応を確認する。診断JSONはcandidateであってincumbentでも実行不能宣言でもない。候補は整数/有理近似でも、全原行/原境界の厳密計算が矛盾を示す場合だけ有効とする。holdoutは使わない。

診断版で2候補を元MPS Fractionへ照合し、node34はR0001単独でmargin15、node70はR0001/27+R0002でmargin3616722361/27000000000の厳密矛盾を得た。行側と全node boundsを検査した。全candidateはLPのscaled counts=0で行/変数名も元MPSと一致。既存のinteger_weightsは正負の小さいanchorを守るため、数値的な小さい逆符号成分を残してしまう可能性がある。小さい成分を落とす近似は候補生成にだけ使い、既存の外向きProblem矛盾検査と元MPS向けguardの両方が受理する場合だけ実行不能候補へ変える案を試す。
