# 報告目的値と元問題からの厳密再計算値

表示された目的値と、保存点を元MPSへ代入した目的値は、binary64の丸めで異なる場合がある。既存の検査器は制約・境界・整数性が絶対1e-6、目的値が相対1e-8*(1+abs(厳密再計算値))である。これはBENCHMARK.mdとcheckerのMIPLIB_ABSOLUTE側に既に定められていた。今回、目的値まで絶対1e-6へ変更する案は採らず、元の基準を保って報告を明確にする。

## 実際の数値例

3変数のbinary、各目的係数-(2^52-1)、制約なしの最小化。主解は全て1、根彩色上界も3なので、主解と最適性は正しい。元MPSでの目的値は-13510798882111485だが、binary64の報告値は-13510798882111484で差1になる。独立GMPはこの差を正確に計算しており、相対許容誤差の範囲内として有効とする。検査器の算術の誤りや実行可能性の誤判定ではない。

最初は「絶対目的値の検査漏れ」を疑ったが、文書と実装を確認して既存の相対方針と一致することを確認した。この経緯と最初のログも残す。目的値が1に近い別例では絶対差1e-7でも相対許容幅2e-8を超えるため不合格となり、単に絶対1e-6へ変えるとこの例の検査を弱める。よって基準の読み替えはしない。

## 変更

validate_solutionはobjective_evaluationにcriterion=relative、相対許容値、厳密な点ごとの許容幅、絶対誤差、元問題からの再計算値、報告トークンを保存する。GMPの目的値合否とこの有理数比較の一致も確認する。arithmeticの表記は「absolute feasibility/integrality, relative objective」とし、何を絶対誤差で判定するか明示する。既存の合否基準は変えない。

benchmark_caseはprimal_bound_exactにGMP厳密再計算値を保存する。互換の浮動小数点primal_boundとnative_primal_boundも残す。bound整合性診断は厳密再計算値で比較し、reference_pointsに使用値・出典・報告値を並べる。旧形式で厳密診断がない場合は警告付きfallback、壊れている場合は失敗とする。

稼働中native snapshotは変更しない。旧snapshotにもstrict_validation.exact.objectiveが保存されており、同じ元解・入力・checker SHAから再最適化なしで有理数の目的値を再利用できる。今回の変更は時間測定やsolver設定、評価許容誤差の変更ではない。許容誤差内の主解と厳密実行可能性証明は引き続き区別する。

## 検査

16CLI集計検証、実際のGMPを呼ぶ2数値例、8preflight、32数値回帰は成功。上の3変数例は実際のRust出力を保存し、GMP・公式・根彩色検査に合格した。数値例でありMIPLIB成績へ加算しない。保存解の厳密目的値は診断表でも-13510798882111485を使い、丸めた表示値へ戻らない。

途中native v2の15入力/39boundでは要確認0・警告0。読み取ったresults bytes/configのSHAを保存する。最初のaudit呼び出しは出力先ディレクトリを作っておらず失敗し、作成後の再実行は成功した。最初のログも保持する。
