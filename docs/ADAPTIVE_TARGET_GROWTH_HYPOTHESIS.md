# 主解修復の時間内訳と適応的な目的改善幅

main122のmap10の10秒出力は適応修復16試行/16改善、約2秒、work16,254,531/100,000,000だった。制約違反行の更新は増分だが、各試行でRepairの索引を再構築し、受理前に全元行を再検査する。まず索引・clone・探索・元点検査の時間を計測し、どこが費用かを特定する。

`examples/adaptive_repair_profile.rs` はmain122のモジュールを隔離コピーし、crate-privateの受理guardもそのまま使う診断用プログラム。production srcは変更しない。最初のビルドは子module解決失敗を検出し、コピー側cuts/binary_graphをmod.rs配置へ修正。元ソース/診断ソース全SHAとビルドログを保持する。base fingerprint8b579cacb175412dに加え、変更した診断コピーのSHAを記録する。

比較は保存済みの検査済み主解からの継続で、MPS読込と最初のseed検査は探索時間外。main同時間比較ではない。2秒/10秒、最大16試行、work1億、同じ点受理条件で探索する。

診断growth=1では成功時に目的改善幅を2倍、失敗時は初期幅まで半減して再試行する。growth=0は従来の一定幅。局所の不能・下界・最適性を返さず、全候補を元問題で検査する。大きな幅で全検査の回数を減らせるかを調べ、結果が良い場合だけmain経路へ移して同時限比較する。主解2例は実験用であり、コード内に問題名や答えを埋め込まない。
