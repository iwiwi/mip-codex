# 双対実行可能性回復の安定候補選択

## 原因の調査

PR70の開発188比較で9問題がnumerical_errorだった。小さいniddaでは、零目的の双対回復が転置解で選んだ列と前進解の分母の不整合で停止した。分母は約−5.12e−10、残り移動量は約46だった。更新基底のLU再分解を最大3回追加するだけの案は、49→66ピボットまで進んだが数値エラーのままで、次に基底特異のLU失敗となった。別問題ran14x18-disj-8は回復処理の4×行数ピボット上限で停止していた。

零目的なので双対比率は同点となる。そこで回復経路だけ、同点なら列番号より大きいピボット分母を優先する案を試した。通常の目的の双対法の候補順序は変えない。

## 一律の安定候補選択は棄却

ranは根LP数値エラーから、1687ピボット・約0.089秒で根LP点を得た。元MPSのFraction検査で境界違反約2e−12、行違反約1.3e−14。LP値3444.42106643829は比較用HiGHSの3444.42106638934と約4.9e−8差で一致した。10秒MIPでは整数解4459.000000195881を得て、GMP絶対誤差・公式検査を通過した（整数性違反0、行違反約2.8e−8）。

同じCPU41・1スレッド・16GiB AS制限・10秒の比較でHiGHS3806/dual3475.6449、SCIP3987/3474.8980、GLPK4538/3458.6224。自作は4459/3444.4211で、GLPKより主解は良いが下界は弱く、HiGHS/SCIPより主解も弱い。native3点はGMP絶対誤差と公式の両方に合格した。最適性や全体優位は主張しない。

しかしneos-860300の60秒は、従来3966/2031から主解なし/2002へ悪化した。最初の根LPが約15.14秒から58.68秒へ長引いた。従来の零目的回復は成功しており、同率選択を変えるとその後のPhase I基底経路が悪化した。一律の安定候補優先は採用しない。188比較は固定snapshotのまま完了・検証して保存する。

niddaの回復上限だけ4→8へ増やした別案も、62→106ピボットとなったが数値エラーのままなので棄却した。

## 現在の仮説: 失敗時だけ再試行

まず従来の候補順序で回復する。NumericalErrorとなり、総期限と反復予算が残る場合だけ、回復前の不変状態を復元して大きいピボットを優先して再試行する。成功していた経路を維持するためのfallbackであり、時間/反復上限、許容誤差、元LP/元MPSの証明・点検査は変更しない。

失敗側で使ったピボット、反転、分解回数の統計と総反復予算を保持する。再試行側の回復内ピボット上限だけは、その呼出しの開始から数える（失敗側が既に回復上限を消費しているため）。総LP反復上限と期限は共通。外側の回復呼出し上限4回は維持する。`lp_restoration_restarts`で実際のfallback回数を記録する。

この版でranの根LPは3476ピボット・約0.269秒となり、同じSHAのFraction検査済み点を得た。neosの60秒比較と回帰を実行中。採用は未定。

一律版はRust209、合成MILP2700、根LP300設定/500出力、数値回帰32件が通過。数値回帰は18有効点と14精度未解決を区別しており、32整数解ではない。binkar根LP12組では時間以外の共通JSON完全一致、回復発動0回。中央値0.078073292→0.0784112405秒（約0.43%増）で非発動の速度改善を主張しない。
